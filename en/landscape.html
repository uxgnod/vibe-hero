Opening: one project, eight commands

Opening question

You asked an agent to scaffold a project. The scripts in package.json read: "dev": "vite dev", "build": "vite build", "typecheck": "tsc --noEmit", "deploy": "wrangler deploy". You install dependencies with pnpm and run scripts with node. Why so many tools? Can't you just write TypeScript and "compile and run" it?

Where the answer lies: turning TS source into "an app people can use" goes through a pipeline: manage dependencies → check types → strip types → bundle and optimize → execute on some runtime → publish to some platform. In Java, the JDK plus Maven fold most of that together; in TS, every step has its own independent, replaceable tool. Each command above is one station on the line.

The pipeline: from a .ts file to a running app

The core principle: type checking and transpiling are two different jobs Deep

In Java a type error means compilation fails: no .class file, the program can't run. TS is different. One of TypeScript's design goals is that types exist only while you write code and are completely absent at runtime. This is called type erasure. The transpiler's job is almost mechanical: delete the type annotations, and what remains is valid JavaScript.

Because "deleting types" doesn't require understanding them, transpilers written in Go or Rust such as esbuild and SWC can process hundreds of thousands of lines per second. Since Node.js 23.6, Node can run .ts files directly (built-in type stripping), and Node 26 makes it stable default behavior. But note: Node only deletes types; it does not type-check.

What this means for driving agents

When an agent says "I ran it and it works", that only tells you the transpiled JS runs — not that the types are right. Your acceptance criteria should explicitly require type checking to pass (e.g. pnpm tsc --noEmit with zero errors), enforced in CI. Chapter 10 makes this part of the pipeline.

TypeScript 7, released in July 2026, rewrote the compiler in Go as a native binary; type checking large projects got roughly 10× faster. It changed the speed, not the language: your code and the typing rules are the same. The practical effect: type checking is now cheap, so there's no excuse to skip it.

Why the frontend needs "bundling" Aware

Go compiles a program into one binary that the server loads from local disk; size and file count barely matter. Browsers are different: code is downloaded over the network to every user's device. A project can have thousands of modules (your code plus what's in node_modules), and fetching them one by one would be unacceptably slow. A bundler solves exactly that:

  • Merging: turn thousands of modules into a handful of files, fewer requests.
  • Tree shaking: keep only code that's actually used; drop unused exports.
  • Code splitting: split by page or route so the first screen only downloads what it needs.
  • Minifying: strip whitespace, shorten names, shrink size.
  • Non-JS assets: CSS, images, fonts — with content hashes in file names for long-term caching.

The two names you'll meet most in 2026: Vite (since Vite 8 it uses the Rust-based Rolldown bundler for everything; TanStack Start, React Router, Astro and SvelteKit are built on it) and Turbopack (Next.js's default bundler). They're in the Aware tier: you'll rarely configure them by hand, and when they fail it's usually an explicit build error.

Runtimes: where JS actually executes

A JavaScript engine such as V8 only executes the language itself: variables, functions, objects. Capabilities like "read a file", "make a network request" or "manipulate the page" are provided by a host environment. Different hosts are different runtimes.

A key fact that lets these runtimes share code: they're all converging on Web-standard APIs — fetch, Request, Response, URL, ReadableStream, crypto.subtle. If your server code sticks to those, it runs unchanged on Node, Bun, Deno and Cloudflare. That's how frameworks like Hono achieve "one codebase, deploy anywhere".

Analogy

Think of V8 as the bytecode execution engine inside the JVM, and a runtime as "the JDK standard library plus the launcher". Java on servers and on Android is the same language with different standard libraries; JS in browsers and in Node is the same language with different host APIs. Where it breaks: JS has no single standard-library publisher; the intersection of the runtimes' APIs is what's portable.

Package management: package.json and node_modules

Every JS/TS project has a package.json at its root — the equivalent of pom.xml or go.mod:

  • scripts: the project's "command menu". pnpm dev runs vite dev. When reading an unfamiliar project, look here first.
  • dependencies vs devDependencies: needed at runtime vs only needed for development and builds.
  • ^19.2.0: a semver range, "any 19.x compatible with 19.2.0". Which exact version gets installed is decided by the lockfile, e.g. pnpm-lock.yaml. Always commit the lockfile.
  • "type": "module": declares modern ES modules (import/export). Chapter 03 explains how that differs from old CommonJS (require).

Which package manager? We recommend pnpm: it keeps all packages in one global content-addressed store and links them, so it's fast and saves disk; and its dependency layout is strict — if a package isn't declared in your package.json, your code can't import it, which prevents "works on my machine" phantom dependencies. npm ships with Node and is the default choice; bun is very fast and a good fit if you already use the Bun runtime.

Supply-chain security (you must know this)

npm dependency trees are deep — a project easily pulls in over a thousand transitive packages — and recent years have seen repeated incidents of malicious packages and hijacked maintainer accounts publishing poisoned versions. Minimum habits: commit the lockfile; use pnpm install --frozen-lockfile in CI; since pnpm 10, dependency install scripts (postinstall) don't run by default — don't casually re-enable them globally; when an agent adds a dependency, require it to state why it's needed, its weekly downloads, and its recent maintenance activity.

The three mainstream stacks of 2026

These three combinations cover most new projects. What they share far outweighs how they differ: TypeScript + React + Tailwind + Zod + Drizzle + Vitest works on all three. The differences are mostly the meta-framework and "where it runs".

▲ The Vercel stack

Next.js (App Router, React Server Components, Server Actions) + shadcn/ui + Postgres (Neon / Supabase) + Better Auth or Clerk + AI SDK → deployed on Vercel.

Strengths: the most material, the most familiar to agents, zero-config deploys.

☁ The Cloudflare stack

TanStack Start / React Router / Hono + Vite + D1 (SQLite) / KV / R2 + Durable Objects + Agents SDK → deployed on Workers.

Strengths: low cost, low global latency, storage and stateful compute built in — great for AI agents and realtime apps.

🖥 The self-hosted stack

TanStack Start / Next.js (standalone output) / Hono on Node or Bun + Postgres + Redis → Docker on a VPS (with Coolify, Dokploy or Kamal).

Strengths: no platform limits, predictable cost, full control over data.

Suggested order of decisions

Learn the shared parts first; choose the platform last. For your first project, pick whichever you can deploy fastest — usually Vercel + Next.js (most material) or Cloudflare + TanStack Start/Hono (lowest cost). Chapter 09 has a finer decision tree.

Interview corner

Q: How do TypeScript and JavaScript relate? How does TS code run?

Key points: TS is a superset of JS that only adds a static type system; types are checked at compile time and fully erased at runtime. TS must become JS before running — tsc can do it, but in practice esbuild / SWC / Vite or Node's built-in type stripping usually do, while tsc only type-checks (--noEmit). So types don't replace runtime validation; external input still needs a library like Zod.

Self-check

1. A colleague ran node app.ts successfully and concluded "the types are fine". Are they right?

No. Node's type stripping deletes annotations without checking them. Running only proves the transpiled JS is syntactically valid. To confirm the types, run tsc --noEmit (or rely on the editor's TS language service).

2. Some server code uses fs.readFileSync to read a local template, and now you're deploying it to Cloudflare Workers. What problem do you expect?

Workers run in V8 isolates without a traditional, freely readable/writable local file system. There's a Node compatibility layer, but "read any file on the deployment machine" doesn't hold. Typical fixes: bundle the template into the code at build time, serve it as a static asset, or store it in R2/KV. The shape of the runtime affects how you write code.

3. Why doesn't a Go backend need the concept of a "bundler" while the frontend can't live without one?

Because frontend code is downloaded over the network into every user's browser. File count, size and caching directly decide load speed; the bundler merges, tree-shakes, splits, minifies and hashes. A Go binary loads from local disk, so none of that applies.
