Setup & Your First Project

Opening: "works on my machine"

Opening question

Same repo. pnpm dev works for your teammate; you get SyntaxError: Unexpected token; the agent's sandbox reports Cannot find module. The code is identical — why are the results different?

Where the answer lies: "the code" is only one input to the result. The other three are the Node version, the package manager and its version, and the exact installed dependency versions (decided by the lockfile). If any of them differs, the result may differ. A reproducible environment writes all three into the repo.

Step 1: install Node through a version manager Use

Don't download the installer from the website. Sooner or later you'll maintain projects that need different Node versions, and a version manager lets each project use its own automatically. We recommend mise (one tool for Node, pnpm, Python, Go and more) or fnm (Node only, minimal).

Node's versioning rule: even-numbered releases become long-term support (LTS); odd ones are short-lived "Current" releases. Use LTS in production. As of September 2026, Node 24 is LTS and Node 26 becomes LTS in October.

Step 2: install pnpm Use

Put "packageManager": "pnpm@10.x.x" (an exact version) in package.json; many tools — including CI and deployment platforms — use it to pick the same package manager version.

Step 3: the editor — your most important learning tool Use

VS Code, Cursor, Zed or JetBrains WebStorm all work. They embed the TypeScript language service: while you type, it type-checks continuously in the background.

The single most useful habit during the transition: hover for types

Hover over any variable, function or component and the editor shows its full type. When reading agent-generated code, this is the fastest way to understand the shape of the data — much faster than reading docs. Cmd/Ctrl-click jumps to the definition, including library type declarations inside node_modules.

Suggested extensions: Biome (format + lint; or ESLint + Prettier), Tailwind CSS IntelliSense (class name hints), Error Lens (shows errors inline at the end of the line).

Step 4: install a coding agent

This guide isn't tied to any one tool. Popular terminal agents include Claude Code (Anthropic), Codex CLI (OpenAI) and pi (open source, minimal, extensible in TypeScript). They all work on the same principles (Chapter 12 takes them apart). Follow each tool's official install instructions; most support npm install -g.

Once installed, do one thing first: in an empty directory, ask it to "describe the environment you're running in" and check it can run node -v and pnpm -v correctly. That confirms the agent's execution environment matches your terminal.

tsconfig.json: these options are all you need to read Use

  • strict is the most important. Turn it off and TS degrades into "JS with hints"; whole classes of bugs (like null access) go unreported. If an agent turns off strict or adds // @ts-ignore to silence an error, that's a signal to stop it.
  • noUncheckedIndexedAccess is off by default but strongly recommended: items[0] might not exist, and that bug is extremely common in production.
  • If you plan to run .ts directly with Node, also consider erasableSyntaxOnly: it forbids TS syntax that generates code (such as enum), guaranteeing types can simply be stripped.

Environment variables: which ones reach the browser Deep

This is one of the easiest mistakes to make and one of the most costly, which is why even a "setup" chapter goes down to the mechanism.

In backend work, env vars exist only inside the server process — naturally private. In a frontend build, however, the bundler replaces certain env var references with literal values at build time, writing them into the JS files sent to browsers. To prevent accidental leaks, frameworks only do this for variables with a specific prefix.

The rule

A variable with a public prefix such as VITE_ / NEXT_PUBLIC_ is effectively published. API keys and database connection strings must never use those prefixes. If the browser needs to call an LLM, the correct approach is for the browser to call your own server, which calls the LLM with the key (Chapter 11).

Self-check

1. You put VITE_OPENAI_KEY=sk-... in .env. It's only used on a "settings" page that requires login. Is that safe?

No. VITE_-prefixed variables are inlined into the JS at build time. JS files are static assets that can be downloaded without logging in (login protects page data, not the bundled scripts). Anyone can open the file and search for the key. Drop the prefix and use it only on the server.

2. Why must the lockfile be committed while node_modules must not?

The lockfile records the exact version and checksum of every dependency, including transitive ones — the key to reproducibility — and it's small text. node_modules can be rebuilt from the lockfile at any time, is huge, and may contain OS-specific binaries.

3. To fix a type error, an agent set strict to false in tsconfig and then reported "type check passes". What do you make of it?

It silenced the check instead of fixing the problem. Turning off strict stops reporting many real defects (like null access). Revert that change, require the agent to fix the specific error under strict mode, and add "never change tsconfig strictness options" to AGENTS.md.
